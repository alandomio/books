**How pairing works (office words)**
- **Source:** docs: docs/mobile-v3/abbinamento.md § In breve (lines 18-26) | **Fact:** 1) at first opening the app creates its own key pair in the phone's keystore, once; 2) it asks the server for a code of **3 characters, valid 24 hours**; 3) the operatore reads the code to the office, the office types it in the back office, sees model and time of the request, chooses the operatore and enables; 4) the app checks **every 30 seconds**; when enabled it shows "Telefono abilitato" and from then on uses every route with the same signature.
- **Source:** docs: abbinamento.md lines 11-16 (decision of 14/10/2026) | **Fact:** «la chiave nasce sul telefono e dura a lungo»; «il server non consegna mai un segreto, il telefono non ne riceve. All'abilitazione cambia solo lo stato.»

- **Source:** docs: abbinamento.md line 3-5 | **Fact:** pairing «Sostituisce `sim_id`/IMSI/IMEI/ANDROID_ID»: the operatore and the commessa come from the pairing, never from the request (abbinamento.md line 183: «`sim_id` non si legge mai da una richiesta»).
- **Source:** docs: abbinamento.md § `POST /v3/pairing` table (lines 125-133) | **Fact:** new phone → registered «in attesa» with a new code; waiting or disabled phone with a valid code → same code; without a valid code (expired or never issued) → new code ("Chiedi un nuovo codice"); enabled → no code.

### § 2 — Quali interventi arrivano sul telefono

**The rule**
- **Source:** code: lib/MobileV3/Bridge/LegacyInterventi.php:10-17 (class doc) | **Fact:** the GOPlanner 3 list is produced by calling the 1.x code (`AndroidController::get_interventi()`) with the operatore's **stored** identifier, «mai quello della richiesta», so the tenant-specific SQL of 1.x stays the same; the list is always the whole list (no "50 nearest" cut).
- **Source:** code: lib/AndroidController.php:360-382 (get_interventi, generic SQL) | **Fact:** generic rule: interventi whose `operatore` is the phone's operatore, whose carico is not «chiuso» (or the intervento has already started), whose `data_pianificata` is between today minus `scadenza_interventi` days and today plus `vedi_interventi_futuri` days (or a tenant custom date filter), AND `stato_id = 3` (Assegnato) OR a tenant-specific extra clause.
- **Source:** code: lib/AndroidController.php:296-345 | **Fact:** the extra clause is `FALSE` by default; with the tenant option `interventi_eseguiti_cell` it adds interventi with stato > 3 of today; some named tenants add their «utente assente» closures (stato 99, or a non fattibile with a tenant code) within `scadenza_utenti_assenti` days and with the carico open.
- **Source:** code: lib/AndroidController.php:226-260 | **Fact:** tenants whose `Intervento` class defines `getInterventiOperatore()` use their own list instead of the generic SQL (the generic window does not apply to them).
- **Source:** docs: docs/mobile-v3/bootstrap-interventi.md:197-199 | **Fact:** «L'elenco della 1.x seleziona gli interventi con `interventi.stato_id = 3` piu', per alcuni tenant, quelli con un esito di assenza: in pratica l'app vede soprattutto `3`, ma deve gestire tutto il catalogo.»

### § 4 — Quando il dato non arriva: coda, rifiuti, segnalazioni e anomalie

**Refusals (errors)**
- **Source:** docs: envelope.md:81-101 | **Fact:** every error carries `retryable`. Retryable: `request_in_progress`, `dependency_pending`, `rate_limited` (429), `internal_error` (500), `unavailable`/`maintenance` (503). Not retryable: 400s, 401 `unauthenticated`/`invalid_key`, 403 `device_revoked`/`device_pending`/`tenant_disabled`/`forbidden`, 404 `not_found`, 409 `idempotency_conflict`/`intervento_locked`/`already_closed`, 413, 415, 422, 426 `client_too_old`.
- **Source:** docs: esito-write.md § Errori (lines 102-121); code: lib/MobileV3/Domain/EsitoWriter.php:102-125 | **Fact:** an esito is refused with:
  - `not_found` (404) when the intervento is unknown **or assigned to another operatore** (`WHERE id_intervento = ? AND operatore = ?`) — the case of an intervento reassigned by the office;
  - `intervento_locked` (409) when stato ≥ 6 («controllato dal backoffice, **mai sovrascritto**»), including 8 and 99; message «Intervento gia' controllato dal backoffice: non si modifica.»;
  - `already_closed` (409) when stato 4 or 5 and time, operatore or content differ; message «Intervento gia' chiuso.»
- **Source:** docs: esito-write.md:76-88 | **Fact:** an identical resend (same time, same operatore, same content) is recognised as `already_applied`: no second write.
- **Source:** docs: envelope.md § Idempotenza (lines 141-165); code: lib/MobileV3/Response.php:127-146 (Response::isStorable) | **Fact:** each write carries an `Idempotency-Key`; same key and same body → the saved answer is replayed, one write only. Saved: only 2xx and non-retryable 4xx; never 5xx, 429 or retryable 4xx; **not saved** either: `intervento_locked` and `already_closed` (`ApiError::STATE_DEPENDENT`), «cosi' lo stesso "Riprova" dopo che l'ufficio ha riassegnato o corretto l'intervento viene rivalutato e puo' passare». Retention 30 days.
- **Source:** code: lib/MobileV3/ApiError.php:45; lib/MobileV3/Response.php:134-145 | **Fact:** `not_found` is **not** in `STATE_DEPENDENT`: being a non-retryable 4xx it **is** saved under the key, so the same send with the same key replays `not_found` (see [CONFLICT] 9).
